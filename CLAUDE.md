## Что это

Мониторит TikTok-аккаунты и публикует их новые ролики в **Facebook Reels**.
Порт проекта [InstagramVideoPublisher](https://github.com/sasha543359/InstagramVideoPublisher)
и [tiktok-instagram-publisher](https://github.com/sasha543359/tiktok-instagram-publisher)
на Facebook. Мониторинг TikTok, уникализатор и цикл «карусель» перенесены
оттуда почти без изменений — они боевые, проверенные, **не переписывать без
причины**.

Владелец — не программист. Репозиторий раздаётся друзьям. Поэтому:
- вся документация и все сообщения в логах — **по-русски**;
- комментарии в коде объясняют **почему**, а не что;
- `appsettings.json` — единственный файл для настройки, каждое поле подписано.

## Жёсткие факты о Facebook Reels API

Проверено по документации Meta (страница обновлена 30.07.2026) и живым
запросам 17.09.2026.

- **Только Страницы.** Личный профиль Reels API не поддерживает вообще.
- **Graph API v26.0** (вышла 29.07.2026). v27.0 не существует.
- **Три фазы**, и вторая живёт на другом хосте:
  1. `POST graph.facebook.com/v26.0/{page-id}/video_reels` + `{"upload_phase":"start"}` → `video_id`
  2. `POST rupload.facebook.com/video-upload/v26.0/{video_id}` ← **другой хост**
  3. `POST graph.facebook.com/v26.0/{page-id}/video_reels` + `upload_phase=finish&video_state=PUBLISHED`
- **Файл можно отдать ссылкой** — заголовок `file_url`. Документация прямо
  разрешает **http, не только https**, так что голый IP годится. Это и есть
  аналог instagram'ового `video_url`.
  Два условия: сайт не должен быть закрыт через `robots.txt` (в `nginx.conf`
  для этого отдаётся пустой 204) и не должен блокировать робота
  `facebookexternalhit/1.1`. Ссылки на `fbcdn` Facebook отвергает.
- **Статус:** `GET /{video_id}?fields=status`, поле `video_status` —
  `ready` | `processing` | `error` (плюс `upload_failed`, `expired`).
- **Обработка начинается только ПОСЛЕ finish** (проверено вживую 18.09.2026):
  до finish `processing_phase` стоит в `not_started` сколько угодно. Поэтому
  до finish ждём только `uploading_phase = complete`, а отказы по самому файлу
  ловим опросом статуса уже после finish. Старая логика ждала обработку до
  finish и теряла на каждой публикации все 300 секунд таймаута.
- **Поле докачки — `bytes_transferred`** (так в живом ответе). В документации
  встречается `bytes_transfered` с опечаткой — код читает оба.
- Итог после публикации: `video_status=ready`, `publishing_phase.publish_status=published`,
  плюс `copyright_check_status`.
- **Обложка — файлом, не ссылкой:** `POST /{video_id}/thumbnails`,
  multipart, поле `source`, `is_preferred=true`, до 10 МБ. Нужны лишние
  разрешения `pages_read_user_content` + `pages_manage_engagement`, поэтому
  шаг необязательный и его провал не отменяет публикацию.
- **Разрешения.** Для публикации нужны три: `pages_show_list`,
  `pages_read_engagement`, `pages_manage_posts`; для обложки ещё два:
  `pages_read_user_content`, `pages_manage_engagement` — их надо и добавить в
  приложение, и отметить в Graph API Explorer при выпуске токена.
  `publish_video` **не нужен** — он про Live Video.
- **Лимит 30 публикаций на Страницу за скользящие 24 часа.** Именно
  скользящие — поэтому `PublishThrottleService` хранит времена публикаций,
  а не счётчик за календарные сутки.
- **App Review не нужен** для публикации на свои Страницы. Приложение живёт
  в режиме разработки навсегда.
- **Токен Страницы бессрочный**, но только если получен по цепочке
  короткий пользовательский → **долгоживущий пользовательский** → `/me/accounts`.
  Пропуск среднего звена даёт токен на 1–2 часа — это ошибка №1.
  Проверено 18.09.2026: отладчик маркеров показывает «Истекает: Никогда».
  **Ловушка:** `debug_token`, вызванный ЭТИМ ЖЕ токеном, показывает дату
  через 60 дней; правду даёт вызов с токеном приложения (`app_id|app_secret`)
  — там `expires_at=0`. «Доступ к данным истекает» через 90 дней публикацию не
  останавливает: разрешения `pages_*` у Meta не истекают.
- В Pages-сценарии `pages_show_list`, `public_profile`, `business_management`
  уже «Готово к тестированию» — «Добавить» нажимается у четырёх остальных.

### Коды ошибок, которые важны

`1363040` соотношение сторон · `1363127` разрешение · `1363128` длительность ·
`1363129` частота кадров — **постоянные**, файл не примут никогда.
Обрабатываются через `PublishResult.IsPermanentlyRejected`: ролик отмечается
в истории как обработанный, иначе он вечно возвращался бы на публикацию.

Кроме этих кодов окончательным считается отказ, который Facebook сообщил в
статусе ПОСЛЕ finish, когда файл целиком у него (`RejectedAfterFinish`): повтор
залил бы тот же файл и получил бы тот же ответ. Код в статусе Facebook часто не
прикладывает — `CodeFromMessage` восстанавливает его по узким фразам
(«resolution too low», «aspect ratio»…). НЕ отказ: `upload_failed`/`expired`
(сбой доставки — ролик уходит в следующий цикл), сорвавшийся опрос статуса
(`ReelStatus.RequestError` — сеть, 5xx, лимит) и таймаут после finish без
ошибки — тогда ролик засчитан опубликованным, чтобы не выложить дубль.
`ProcessingTimeoutSeconds` действует дважды: до finish (загрузка) и после (выход).

## Ловушки, на которые уже наступали

### Сценарий использования нельзя удалить

Meta: «Сценарии использования нельзя удалить после создания приложения», и
часть их несовместима между собой. **Нельзя добавлять Pages-сценарий в
приложение, которым публикуется Instagram** (`VideoAutoPost`, App ID
`2044899879590453`) — откатить будет нечем. Под Facebook Reels заводится
отдельное приложение.

### curl-cffi должна быть ровно 0.16.0

С 0.16.1 появляется отпечаток `chrome-150`, `yt-dlp` выбирает самый свежий
автоматически, а **TikTok блокирует chrome-150 наглухо**
([yt-dlp #17604](https://github.com/yt-dlp/yt-dlp/issues/17604)).
В `Dockerfile` стоит extra `pin-curl-cffi` (официальный у yt-dlp), а entrypoint
обновляет yt-dlp с `--upgrade-strategy only-if-needed` и проверяет версию.
`pip install -U curl-cffi` внутри контейнера ломает скачивание.
`--impersonate chrome-146` это **не лечит** — экстрактор передаёт «любую» цель
и она пересиливает флаг.

### 90 секунд

Роликов длиннее в TikTok много (замер: у @nasa первый же попавшийся был 144 с).
Facebook такие не принимает. Подрезка **до 89,5 с, а не до 90**: `-c copy` режет
по границам пакетов и промахивается вверх — при запросе 90,0 реально вышло
90,067, что уже за пределом.
Подрезка живёт в двух местах: `uniquify.py` (когда уникализатор включён) и
`VideoUniquifierService.EnsureReelsDurationAsync` (работает **всегда**, даже с
выключенным уникализатором).

### Токен в логах

Штатный логгер `HttpClient` печатает URL целиком, а токен ездит в строке
запроса. В `Program.cs` стоит
`builder.AddFilter("System.Net.Http.HttpClient", LogLevel.Warning)` **после**
`AddConfiguration`, чтобы фильтр нельзя было снять из `appsettings.json`.
Логи смотрят через `docker compose logs` и пересылают друг другу — живой токен
Страницы там появляться не должен.

### `--postprocessor-args "Merger:…"` применяется не всегда

Merger запускается только когда yt-dlp реально склеивает отдельные дорожки.
Для готового muxed-формата он не срабатывает, и `-ar 48000` не применяется.
Поэтому приведение звука к 48 кГц стерео дублируется в `uniquify.py`.

### Питч-фильтр и частота дискретизации

`asetrate` подменяет частоту, `atempo=1/pitch` возвращает скорость. База должна
быть **реальной частотой источника**: в инстаграмной версии стояло жёсткое
`44100`, и на 48-килогерцовом исходнике звук уезжал на 8% — видео и звук
расходились. Теперь частота берётся из `ffprobe` (`meta["ar"]`).

### Первый запуск молчит

Программа запоминает последние 5 роликов каждого автора и ждёт новых. Это
не поломка. Потеря `video_history.json` выглядит так же — поэтому файл лежит
в `/var/www/videos` (том с хоста), а не в рабочем каталоге контейнера.

### `docker compose up -d` без `--build`

`appsettings.json` вшивается в образ при сборке. Без `--build` поднимаются
старые настройки, и кажется, что правки не применились.

## Требование заказчика

Аудитория — русскоязычная: СНГ (Беларусь, Украина, Казахстан, Россия…) и
русскоязычные в Европе. «Ограничения по странам» у Страницы СКРЫВАЮТ её везде,
кроме перечисленных стран (проверено 18.09.2026) — оставлять пустыми. Охват
русскоязычных — через язык: подписи из TikTok, `DefaultHashtags` (русские).


**В описании каждой публикации обязана быть строка `Twitch: MELLSTROY`.**
Реализовано как `RequiredCaptionSuffix` в корне `appsettings.json` —
добавляется ко всем публикациям автоматически, и к `CustomCaption` тоже.
Дублирования нет: если строка уже в тексте, второй раз не добавляется.
Специально сделано одной общей настройкой, а не полем у каждой Страницы —
чтобы её нельзя было потерять при правке одной из Страниц.

## ИНСТРУКЦИЯ.pdf

Собирается скриптом `docs/instruction/make_pdf.py` (reportlab + Pillow, шрифты
Windows), скриншоты — `docs/instruction/shots/`, сняты 18.09.2026 на тестовом
аккаунте. Править PDF руками нельзя — только скрипт и пересборка:
`python docs/instruction/make_pdf.py`. Шаги пронумерованы 1–23; ссылки «шаг N»
разбросаны по тексту, при вставке шага их надо пересчитать. В `code()` символ
`&` экранируется — без этого ссылка обмена токена в PDF ломалась (`&client;_id`).
На скриншотах не должно быть почты, токенов и секретов (затирать перед вставкой).

## Чего НЕ делать

- Не переписывать `TikTokMonitorService` — он выстрадан, там каждый флаг
  и каждая проверка стоят по конкретной причине, описанной в комментариях.
- Не убирать запасной путь скачивания через `PlayAddr`: `yt-dlp` на TikTok
  падает 2–4 раза из 6, особенно с дата-центрового IP.
- Не менять `-S res,br` на что-то «поумнее» без замеров.
- Не переводить лимит публикаций на календарные сутки.
- Не публиковать ничего в аккаунт владельца без явной просьбы.
